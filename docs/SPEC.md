# GoldStack — Project Specification

GoldStack is a digital gold investment platform (like Jar, Paytm Gold, PhonePe Gold), built as a learning and resume project. The developer is a **beginner in backend development**.

## 1. What the app does
=====================================================

Users hold **VIRTUAL** coins (not real money; 1 coin = ₹1) and use them to buy and sell gold in grams.

- **Signup/login (JWT).** New users get a starting bonus of virtual coins; a mock endpoint lets them "top up" coins.
- **Live gold price**, updated every few seconds and pushed to the browser via WebSocket.
- **Buy/sell gold** using a price quote locked for 5 minutes. Buying requires a valid quote ID; expired quotes are rejected.
- **Portfolio:** total grams, total invested, current value, profit/loss, return %, full transaction history with pagination.
- **"What if" calculator:**
  - a) **Lump sum:** "If I invested X coins on date D, what is it worth today?"
    - `grams = amount / price_then`
    - `value_now = grams * price_now`
    - `return% = (value_now - amount) / amount * 100`
  - b) **SIP what-if:** "If I invested X coins every day/week/month from date D, what would I have today?" Return a time series (invested vs value) for charting.
  - Seed several years of historical daily gold prices (from a CSV, or generated by a realistic simulator) so this works out of the box.
- **Daily auto-debit (SIP):** users create, pause, resume, cancel SIPs (amount, frequency, start date). A scheduled job buys gold automatically. If coins are insufficient, mark it failed, notify the user, retry next cycle.

## 2. Tech stack
=====================================================

- **Backend:** Java 21, Spring Boot 3 (Web, Data JPA, Security, Validation, WebSocket, Actuator), Maven
- **Frontend:** React + TypeScript + Vite, Recharts for charts
- **Database:** PostgreSQL with Flyway migrations
- Redis (Spring Data Redis), Kafka (Spring for Apache Kafka)
- Spring Cloud Gateway, OpenFeign, Resilience4j, ShedLock
- Docker + docker-compose, Kubernetes (kind or minikube)
- **Testing:** JUnit 5, Mockito, Testcontainers
- **API docs:** springdoc-openapi (Swagger)
- **Observability:** Prometheus, Grafana, distributed tracing (Micrometer Tracing + Zipkin)
- **CI:** GitHub Actions

=====================================================
## 3. Non-negotiable rules
=====================================================

- **NEVER use double/float for money or grams.** Use `BigDecimal`: coins to 2 decimals, grams to 4 decimals, with explicit `RoundingMode`.
- **Double-entry ledger** for coins and gold: every movement writes matching debit and credit entries; ledgers must always reconcile.
- **Idempotency:** every buy, sell and SIP debit carries an idempotency key so nothing ever executes twice. SIP key = `sipId + date`.
- **Prevent concurrent overspending** with row locking or optimistic locking.
- **Global exception handling** with consistent JSON error responses and correct HTTP status codes.
- **Input validation** on every request.
- **No secrets in code:** use environment variables (and Kubernetes Secrets later).

## 4. Target architecture (final state, reached in Phase 5)
=====================================================

### Services (each owns its own PostgreSQL database)

| Service              | Responsibility                                   | Main tables                     |
|----------------------|--------------------------------------------------|---------------------------------|
| api-gateway          | Single entry, JWT check, rate limiting, routing  | -                               |
| user-service         | Signup, login, profile                           | users                           |
| wallet-service       | Virtual coin balances + ledger                   | wallets, ledger_entries, outbox |
| price-service        | Fetch price, store history, broadcast live price | price_history                   |
| order-service        | Quotes, buy/sell, gold holdings                  | orders, gold_holdings, outbox   |
| sip-service          | SIP schedules and daily execution                | sips, sip_executions, shedlock  |
| portfolio-service    | Holdings view, P&L, what-if calculator           | read models built from events   |
| notification-service | User alerts                                      | notifications                   |

### Communication

- **Synchronous REST via OpenFeign** when an answer is needed immediately (e.g. order-service asks price-service for the price).
- **Asynchronous Kafka events** for everything that "happened".

### Kafka topics

| Topic               | Producer | Consumers                           |
|---------------------|----------|-------------------------------------|
| gold.price.updated  | price    | portfolio, gateway (WebSocket push) |
| order.placed        | order    | wallet                              |
| order.completed     | order    | portfolio, notification             |
| order.failed        | order    | wallet (refund), notification       |
| sip.debit.requested | sip      | order                               |
| sip.debit.failed    | order    | sip, notification                   |
| notification.send   | any      | notification                        |

### Redis keys

| Key                     | Purpose                           | TTL               |
|-------------------------|-----------------------------------|-------------------|
| gold:price:latest       | Current gold price                | overwritten often |
| quote:{quoteId}         | Locked price + grams              | 5 minutes         |
| idem:{key}              | Result of a completed request     | 24 hours          |
| ratelimit:{userId}      | Request counter                   | 1 minute          |
| whatif:{amount}:{date}  | Cached calculator result          | 1 hour            |

### Key flows

- **Buy:** get quote (saved in Redis, 5 min) → confirm with quoteId + idempotency key → wallet debits coins → gold credited → `order.completed` event. If crediting gold fails, a compensating refund returns the coins (orchestrated Saga). Use the **Transactional Outbox** pattern so events are never lost. Kafka consumers must be **idempotent**.
- **SIP:** daily scheduler (ShedLock so only one instance runs it) → find due SIPs → publish `sip.debit.requested` per SIP → order-service buys at current price → success notification, or `sip.debit.failed` + retry next cycle.
- **Price:** a `PriceProvider` interface with two implementations: a random-walk simulator (default) and a pluggable real gold price API adapter. Every few seconds: save to `price_history`, update Redis, publish `gold.price.updated`, push via WebSocket. Resilience4j circuit breaker around the external API, falling back to the last cached price.

## 5. Phases
=====================================================

### PHASE 0 — Setup
- Monorepo: `/backend`, `/frontend`, `/infra`, `/docs`. `.gitignore`, root README skeleton, `/docs/SPEC.md`, `CLAUDE.md`.
- Check installed tools (java, mvn, node, docker) and report anything missing.

### PHASE 1 — Single Spring Boot app (learn the logic first)
- Implement ALL features from section 1 in ONE app (a "modular monolith", one package per future service), using PostgreSQL in docker-compose.
- Use Spring `@Scheduled` for price fetching and SIPs.
- Show the data model and explain the double-entry ledger BEFORE writing code.
- Unit tests for the what-if math and ledger; a concurrency test proving two simultaneous buys can't overspend.
- Swagger docs; README section listing every API route.

### PHASE 2 — React + TypeScript frontend
- Pages: login/signup, dashboard (live price ticker, coin balance, gold holdings, P&L), buy/sell with a quote countdown timer, portfolio with chart, what-if calculator with charts, SIP management.
- Generate an idempotency key per buy attempt. Handle loading, errors, expired quotes, insufficient balance.

### PHASE 3 — Docker
- Multi-stage Dockerfiles for backend and frontend; docker-compose runs everything with ONE command.

### PHASE 4 — Redis
- Add every Redis use from the Redis keys table. Explain each use and show how to inspect keys with `redis-cli`.

### PHASE 5 — Microservices + Kafka
- Split the monolith into the services in section 4, each with its own database.
- Add Spring Cloud Gateway, OpenFeign, Kafka topics, Saga with compensation, Transactional Outbox, idempotent consumers, ShedLock, Resilience4j.
- Add a Kafka UI container to watch events flow.
- Mermaid sequence diagrams of the buy, sell and SIP flows (success + failure) in `/docs`.

### PHASE 6 — Observability and testing
- Actuator + Prometheus + Grafana (with a dashboard JSON committed), distributed tracing with Zipkin.
- Integration tests with Testcontainers (Postgres, Redis, Kafka) for the buy Saga and SIP flow.
- A reconciliation job that verifies coin and gold ledgers always balance, and alerts if not.

### PHASE 7 — Kubernetes
- Manifests in `/infra/k8s` for kind or minikube: Deployment + Service per app, Ingress, ConfigMaps, Secrets, liveness/readiness probes on `/actuator/health`, resource limits, and an HPA for order-service.
- Explain each Kubernetes object as it is written. Give the exact commands to deploy, check pods, view logs, and scale.
- Demonstrate: kill a pod and watch it restart; scale sip-service to 3 and show ShedLock keeps the SIP job running once.

### PHASE 8 — CI/CD and portfolio polish
- GitHub Actions: build, test, and build Docker images on every push.
- Final README: project summary, architecture diagram (Mermaid), tech stack, how to run in one command, API docs link, Postman collection, screenshots/GIF of the live price and what-if charts, and a "Design decisions" section (why Kafka, why Redis, Saga, Outbox, idempotency, ShedLock).
